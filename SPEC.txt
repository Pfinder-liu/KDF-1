KDF-1 v1 candidate specification / 候选规范

Status: NOT FROZEN / 尚未冻结. This revision narrows KDF-1 to deterministic
passwords for a few critical recovery-root accounts. It does not define private
keys, passkeys, or a general password manager. HRC-1 below is an encoding of the
existing Recovery Secret, not a service-provider recovery credential.

The following rules are normative for both the Python API and interactive CLI.
Changing any accepted input's derived bytes after freezing requires a new scheme
version. Passing the reference vector is necessary, but does not alone establish
full conformance or security.

1. Inputs and canonicalization

Master Phrase

Must be nonempty and contain only the fixed KDF-1 v1 repertoire in Appendix MP.
Validate the ORIGINAL input before normalization. CR U+000D and LF U+000A are
forbidden anywhere, including CRLF and leading/trailing line breaks. Reject;
never strip them, convert CRLF to LF, or continue with a modified secret.
Unpaired UTF-16 surrogates, all scalars outside Appendix MP, and all non-text
inputs are invalid. Do not substitute, transliterate or guess rejected input.

The repertoire is Unicode 13.0.0 assigned scalar values, minus CR/LF, exactly
listed as inclusive ranges in Appendix MP. It is NOT the host's assigned set.
Private-use scalars are included (General_Category=Co); noncharacters and points
unassigned in Unicode 13.0 are excluded. Newer assigned characters are still
invalid for KDF-1 v1. Chinese and other languages assigned in the baseline remain
supported. The table, not a category query against a changing runtime, governs.

After validation, use standard Unicode 13.0 NFC, then UTF-8. A conformant NFC
implementation supporting Unicode 13.0 or later may be used: Unicode normalization
stability guarantees identical NFC for these baseline-assigned strings. Older or
nonconformant NFC runtimes are unsupported; fail rather than substitute output.
Do not use stream-safe normalization or insert CGJ, trim, lowercase, case-fold,
apply NFKC, or replace unencodable characters. Spaces (including leading/trailing),
tabs and other allowed scalars are significant. Whitespace-only phrases without
CR/LF are technically accepted but unsuitable secrets. No locale encoding.

master-phrase-vectors.json fixes public NFC/UTF-8 and three KDF outputs for legal
inputs, plus illegal-input examples. Startup tests include Unicode13-era NFC and
rejection cases. Conformance requires the complete input contract, not just a
successful vector. Official Unicode13 data/conformance suite is archived for
future implementers; the Calculator does not load a Unicode database or runtime.

Permanent label and optional account label

label replaces the former service field. The user chooses a stable identifier
such as apple-root or primary-email; it is independent of the current domain,
URL, email address, account display name, or company name.

Apply these steps in order to both labels:

1. Remove leading/trailing characters from the exact ASCII whitespace set
   U+0020, U+0009, U+000A, U+000D, U+000B, U+000C.
2. Validate the remaining string: only A-Z a-z 0-9 . _ -, at most 128 characters.
   label requires at least one character. account may be empty (default "").
3. For label only, replace ASCII A-Z with a-z. Preserve account case.
4. Encode as ASCII (identical to NFC + UTF-8 for this accepted alphabet).

There is no Unicode case conversion, transliteration, compatibility normalization,
URL parsing, registrable-domain lookup, www. removal, or aliasing. Non-ASCII
labels, internal whitespace, |, /, :, and @ are rejected, not repaired.
NFC must not be applied before label validation to turn a non-ASCII lookalike into
ASCII. For example, K is invalid. Full email addresses are not account labels;
use a stable alias such as personal.

Examples:  APPLE-ROOT  equals apple-root; account Personal differs from
personal; example.com differs from www.example.com; https://example.com
is invalid. Old domain-shaped labels such as example.com remain valid opaque
identifiers. Store the canonical values printed by the CLI in recovery records.

Revision and password length

Revision is an integer in 1..4294967295, default 1. The context uses its
canonical base-10 representation without sign or leading zeroes.
Length is an integer in 8..1024, default 24. Length is not part of the HMAC
context: shorter outputs are prefixes of longer ones, not independent passwords.

The Python API accepts actual integers, excluding booleans, floats and strings.
The CLI removes the same ASCII whitespace at the ends, accepts only ASCII digits,
and parses base 10. Empty CLI input selects the default; 001 means revision 1.
Invalid metadata is rejected before running Argon2.

Recovery Secret

Exactly 16 cryptographically random bytes (128 bits). Human representation:
HRC-1 is the default paper representation (defined below). The compatibility/expert representation is 32 hexadecimal digits. Hex parsing removes only the six ASCII whitespace characters
listed above, anywhere in the representation; then exactly 32 characters in
0-9 a-f A-F must remain. No 0x prefix or Unicode whitespace is accepted.
The raw-byte master-key API also checks for exactly 16 bytes.

This is secret recovery material. Although used to derive an Argon2 salt, neither
the Recovery Secret nor that salt should be published or logged.

2. Master KDF (unchanged)

argon2_salt = SHA-256(ASCII("KDF-1-v1|argon2-salt|") || recovery_secret)[0:16]

master_key = Argon2id_v19(password=UTF8_NFC(master_phrase), salt=argon2_salt, m=65536 KiB, t=3, p=1, outlen=32)

[0:16] means the first 16 bytes. The domain prefix is part of the algorithm;
hashing the Recovery Secret alone is incompatible. Parameters are explicit and
must not follow changing library defaults. There are no optional Argon2 secret
or associated-data inputs.

3. Per-account key (historically named site_key)

context = ASCII("KDF-1-v1|" + canonical_label + "|" + canonical_account + "|" + decimal_revision)

site_key = HMAC-SHA256(key=master_key, message=context)

The master key is exactly 32 bytes. With the empty account, both separators remain,
e.g. KDF-1-v1|apple-root||1. Labels cannot contain |, so field boundaries are
unambiguous. Both derive() and site_key() enforce canonicalization and bounds.

4. Password stream (unchanged)

For counter = 0 through 2^64−1:

block = HMAC-SHA256(site_key, ASCII("KDF-1-v1|password-stream|") || uint64_be(counter))

The key is exactly 32 bytes. The counter occupies exactly eight unsigned,
big-endian bytes. Concatenate blocks in order. Exhaustion is an error.

5. Password encoding (unchanged)

Alphabet, in exact order (74 characters):

ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789!@#$%^&*-_=+

limit = 256 - (256 mod 74) = 222. Reject each stream byte b >= 222;
otherwise append alphabet[b mod 74]. Stop at the requested length. No shuffling,
character-class enforcement, replacements, or retrying whole passwords occurs.
An output is not guaranteed to contain all four character classes.

6. Reference test and exits

test_vectors.json contains public inputs and fixed expected values for the
master key, per-account key and password. --self-test reads the file beside
kdf.py, compares all three fields exactly, prints PASS and exits 0 only when all
match. Missing/malformed data, a wrong scheme, null outputs or mismatches produce
FAIL and exit 1. It never writes or regenerates expected values.

Interactive success exits 0; invalid input/derivation failure or unavailable hidden
secret input exits 2; interruption/end-of-input exits 130. Argparse syntax errors
exit 2. These CLI details apply only to the Python reference implementation. The primary Recovery Calculator is the self-contained local RECOVER.html described below; it needs no Python installation.

7. Pre-freeze compatibility changes

The supplied ASCII reference vector is unchanged: the canonical context remains
KDF-1-v1|example.com|test|1. Cryptographic algorithms, prefixes, parameters,
alphabet and sampling are unchanged.

API keyword service is renamed to label; positional argument order is unchanged.
Old CLI trimming/case conversion now happens in the core API as well. Previously
accepted Unicode labels, email-like account strings, separator-containing inputs,
empty main labels, nonpositive/out-of-range revisions and unbounded lengths are
rejected. Uppercase/spaced main labels supplied directly to the old API now
canonicalize and may yield different outputs. Unicode whitespace in hex input
is no longer stripped. These are deliberate candidate-stage input-contract changes.

The old unrestricted delimiter format allowed service='a|b', account='c' and
service='a', account='b|c' to share one context. Rejecting delimiters fixes this
without changing the byte format for valid labels.

The A1/A2 candidate repair additionally rejects all original phrase scalars not
in Appendix MP, including PUBLIC\u0897\u0323, and every CR/LF. Previously conflicting
edge-input outputs are not preserved. Existing public KDF outputs remain unchanged.

Before freezing, approve these input rules and limits, independently reproduce
the vectors, review the design and perform recovery drills on intended devices.

8. HRC-1 Human Recovery Code (candidate encoding, independent of KDF v1)

Alphabet in exact digit order, values 0..23:
23456789ABCDEFGHJKMNPQRS
There are 24 symbols. O, I, L, 0 and 1 are not accepted or substituted.

Data capacity: 24^30 > 2^128 (approximately 137.55 bits). Therefore every
16-byte secret is represented, without losing entropy. Extra capacity is NOT
extra entropy. Secret creation, in a future enrollment tool, must use an OS
CSPRNG to obtain exactly 16 uniformly random bytes. The Calculator now provides a separate Create NEW Recovery Code action.
It calls browser crypto.getRandomValues(new Uint8Array(16)), encodes those exact
16 bytes with the existing HRC-1 rules, and displays only the Human Code. It never
uses Math.random, a server or a weaker fallback. Failure STOPs. Mutable secret
bytes are cleared after encoding; the displayed code remains until closed/replaced.
A newly generated Recovery Code cannot recover passwords created with a different
Recovery Code. Creation never overwrites the existing recovery form.

Interpret the 16 bytes as an unsigned big-endian integer n. Encode n in radix
24 using exactly 30 digits, most significant first, left padded with digit 0
(the character '2'). Compute the integer checksum:
  c = sum((i+1)*digit[i], i=0..29) mod 571
571 is prime. Append alphabet[c div 24], then alphabet[c mod 24].
Display six groups of five data symbols, then two checksum symbols:
XXXXX-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX-XX
Exactly 32 symbols / 38 displayed characters. Leading '2' digits are significant.

Decode: remove only ASCII '-' and the six ASCII whitespace characters specified
in section 1 anywhere. Convert only ASCII a..z to A..Z. Require exactly 32
symbols from this alphabet. Do not accept Unicode hyphens, Unicode whitespace,
lookalikes, alternate characters, or intelligent corrections. Check that the
last two digits equal the computed c. Values 571..575 cannot be checksums.
Convert the first 30 digits to integer n; reject n >= 2^128, never truncate.
Return exactly 16 big-endian bytes (including leading zero bytes).
Decode before invoking Argon2. HRC-1 does not alter the KDF salt or any v1 output.
The Python kdf.py hex API remains unchanged for compatibility; human_code.py
adds the reversible layer. The Calculator accepts only HRC-1, removing ambiguity
between a 32-symbol human code and 32-hex input.

Error detection, NOT authentication:
A changed data digit contributes delta*(i+1), whose absolute value is at most
23*30=690. Since 571 is prime and neither nonzero delta nor i+1 is divisible by
571, every single data-symbol substitution changes c. Every single checksum
symbol substitution is also rejected. An adjacent swap of unequal data symbols
contributes their nonzero difference (absolute value <=23), so is detected.
Insertions/deletions change the symbol count and are rejected. Identical-symbol
swaps have no effect. Some multiple errors cancel; checksum is NOT an adversary
barrier or proof of the correct secret. Tests cover data/checksum boundary swaps
for public vectors; no universal guarantee for boundary or group swaps is made.
Uniform random checksum guesses pass with probability 1/576 before range checks.

9. Authority, recovery model and Calculator contract

KDF-1 remains CANDIDATE / NOT FROZEN. The normative algorithm is this SPEC.txt
and fixed public vectors, independent of programming language and packaging.
Python is a reference implementation. Native implementations must also enforce
input rules; passing one vector alone is insufficient. Future implementations must enforce the fixed Appendix MP repertoire BEFORE
NFC and UTF-8; host Unicode updates cannot enlarge the input set. The cryptographic derivation in sections 2..5 is unchanged; section 1 now fixes
the candidate-stage Master Phrase repertoire and rejects CR/LF.

Durable material: paper Recovery Code; a strong remembered Master Phrase stored
separately; exact canonical label/account/revision/length; SPEC and public vectors.
Two parts are both required. Paper disclosure allows OFFLINE guesses of the
Master Phrase, so a weak phrase is not rescued by a paper code. Losing the phrase
cannot be repaired by the code. Keep a home backup and an accessible travel copy;
travel paper need not expose account/email identity. Preserve metadata separately
if omitted from travel paper. Service-provider recovery remains a separate path.

RTO target: <= same day; drill target <=30 minutes on a trustworthy replacement
computer, with no original device and no internet. Offline recovery also requires
access to a previously saved Calculator or SPEC/vectors. Paper alone cannot supply
missing software to a completely empty offline computer. Keep a portable copy
accessible away from home; a printed SPEC helps future reimplementation but is
not a 30-minute substitute for a working calculator.

Calculator startup verifies exact embedded vendor/core/vector payload SHA-256
checksums, then a complete public KDF reference test (master key, site key,
password), four Human Code vectors and ability to allocate/run Argon2. Fields
remain disabled until SELF TEST PASS. Failure displays STOP and root cause;
users must not enter secrets. If all JavaScript is disabled or the bootstrap is
blocked/missing, the static page stays STOP with all fields disabled. No source
loader, HTTP server, installation, package manager, working copy or network is
required. file:// is the primary opening method. Non-file navigation is rejected.

The Calculator is one self-contained RECOVER.html. JavaScript, Argon2/BLAKE2 WASM,
public vectors, CSS and system-font layout are embedded. No CDN, remote script,
font, fetch/XHR, WebSocket, WebRTC, worker, updater, account, telemetry, database,
auto-identification or storage API is used by the delivered Calculator.
Argon2id uses pinned hash-wasm 4.12.0, outputType=binary, iterations=3,
memorySize=65536 KiB, parallelism=1, hashLength=32, Argon2 version 19. SHA-256
and HMAC-SHA256 use browser Web Crypto, explicitly selecting algorithms.
UTF-8 is TextEncoder; NFC is String.normalize('NFC') ONLY after fixed Appendix MP
validation, including rejection of CR/LF and surrogate code points. uint64 stream counters use BigInt and exactly
8 big-endian bytes. No home-made cryptographic primitive or weak fallback.

CSP: default/connect/worker/frame/object/img/font/media/manifest-src 'none';
form-action/base-uri 'none'. Script and style blocks are allowed only by SHA-256
hashes. script-src additionally permits 'wasm-unsafe-eval' to compile embedded
WASM; it does NOT permit JavaScript 'unsafe-eval' or 'unsafe-inline'. The vendor
compiles embedded bytes directly; it does not fetch a WASM URL. Actual tested
browser/version/CPU matrix and negative CSP tests are in COMPATIBILITY.txt.
CSP is a useful connection restriction, not an operating-system air gap or
universal browser isolation. It does not isolate browser extensions, compromised
hosts, browser telemetry or unrelated browser tabs. Physical disconnection is
still the human drill condition. Browser-level auto-fill may be offered despite
autocomplete=off; this page never requests credential saving or copies to clipboard.

Integrity limits: payload hashes and CSP catch accidental data/script damage.
They do not authenticate an attacker who replaces the entire HTML, expected
hashes and CSP together. Bootstrap/static HTML is not self-authenticating.
A trusted acquisition/storage path and host/browser are still required.
INTEGRITY.json is developer/archive inventory; emergency users do not run hashes.
No claim of an independent security audit of this candidate or its vendor is made.
Vendor provenance/license/pinned archive, readable C/TypeScript sources and exact
Argon2/BLAKE2 WASM bytes are preserved in developer/vendor for future audit.

Master Phrase defaults hidden; an explicit Show/Hide button changes only input
type, not value/normalization/encoding. It returns to hidden after phrase clearing.
Hidden input mainly limits accidental shoulder viewing; it cannot prevent a
keylogger or a compromised host. Paste is permitted. Recovery Code stays visible. Code and metadata errors are
checked before expensive real KDF. Raw paste/drop and beforeinput events reject
CR/LF before the single-line control can sanitize them. A rejected edit clears the
phrase/output, displays STOP and blocks derivation until a new verified edit.
Unavailable raw paste data is refused with a manual-entry instruction. An input
event cannot unlock a rejected edit merely because the host removed its newline.
Normal single-line paste and Show/Hide remain available. Exact fields only; no identity
or website guessing. No inputs are written to files, logs, clipboard or storage
by the page. Output is visible/selectable; close the tab when finished.
Mutable arrays are cleared where practical, but JS strings, WASM vendor memory,
browser history/cache/crash handling/swap cannot guarantee zeroization or absence
of capture. This is a recovery calculator, not an isolated security enclave.

All platforms receive the SAME HTML. Intel Mac is a required acceptance target;
passing on Apple Silicon is not Intel verification. Intended matrix: Intel/M-series
Mac Safari/Chrome, Windows Edge/Chrome, Linux Firefox/Chrome. Untested combinations
are explicitly UNTESTED. Supported-browser capability requirements are BigInt,
Unicode NFC, TextEncoder, Web Crypto SHA/HMAC in file://, WebAssembly compilation
under the hash CSP and at least 64 MiB available to Argon2. No installation or
local-server workaround is in the emergency flow. An unsupported browser must
STOP; do not reduce Argon2 memory/iterations to make it run.

Python remains the reference implementation and developer verification path.
Previously supplied native ARM64 app is optional historical convenience, not the
primary entrance or long-term dependency. It is not included in this web kit.
No new native cross-platform packaging/runtime system is introduced.

Anonymous Travel QR representation (candidate UX addition, not a KDF revision)

Payload is exactly the canonical grouped Human Recovery Code returned by the
existing HRC-1 encoder: six groups of five symbols, hyphens, final two symbols.
No prefix, URL, newline, date, label, account, revision, phrase, keys, password
or other metadata. Decode QR text with the unchanged Human Code decoder to
obtain the same 16 bytes. QR generation consumes no new random secret.

The current calculator uses QR Code Model 2, alphanumeric encoding, error
correction H, automatic smallest fitting version and automatic mask selection.
It renders pure black/white modules with a four-module white quiet zone on
all sides, no logo/text. Current 38-character payload gives version 4, 33x33
modules, 492x492 opaque PNG (12 pixels/module including quiet zone).
Different conforming QR encoders may choose other masks/versions; the decoded
text, not the matrix, is authoritative. No scanner belongs to the calculator.

Anonymous means no visually printed context; it is NOT encryption or a promise
that the code's format is unrecognizable. Anyone scanning/copying/photographing
the QR acquires this Recovery Code and may guess the Master Phrase offline.
Keep the phrase separately. To replace an exposed secret, create a new code,
derive and actually set replacement passwords on the affected accounts, and
update backups/records. Incrementing revision alone does not revoke the old
Recovery Secret. QR cannot recover any password made with another secret.

PNG export contains only the QR raster, with generic filename card.png.
Print QR only removes all document text. Browser-generated print headers and
footers must be disabled by the user; the page cannot reliably control them.
Print at least 45 mm square including quiet zone, at normal scaling. Retain the
white margin. H error correction is not a guarantee against any particular fold,
damage, printer, camera or decades of aging. Do a real scan after printing.

to decide membership. Each token A-B includes both endpoints, hexadecimal Unicode

extensions. Count: 679 disjoint sorted ranges, 281390 scalars. CR/LF and surrogates
are absent. JSON mirror: master-phrase-repertoire.json. Source: official Unicode
13.0.0 UnicodeData.txt, expanding First/Last records, dropping D800-DFFF, 000A,
and 000D. Do not regenerate from a newer UCD. Standard normalization is Unicode
NFC (UAX #15), with no extra transformation; NFC for this fixed repertoire remains
stable in later conformant Unicode versions. The official UCD source and
